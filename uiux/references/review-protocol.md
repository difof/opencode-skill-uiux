- Use this guide for UI, UX, visual, interaction, accessibility, responsive, or performance review; an audit is read-only unless the user also requested fixes, and the report must distinguish observed behavior, code-derived risk, unverified assumptions, and subjective design preferences.
- Establish the target routes, components, users, task, platform, states, design contract, and requested depth before reviewing; preserve scope and inspect the existing identity before judging deliberate choices.
- Load the complete [Impeccable critique](../upstream/impeccable/reference/critique.md) for cognitive load, all ten usability heuristics, persona stress tests, specificity, scoring, severity, and reporting; use [web audit](../upstream/impeccable/reference/audit.md) or [native audit](../upstream/impeccable/reference/audit.native.md) for technical quality.
- Keep evidence from product usability, rendered design, source implementation, browser/device behavior, and automated checks distinct; a screenshot cannot prove keyboard behavior, a static scan cannot prove task success, and a polished appearance does not establish correctness.
- Review the task path first: can the intended user discover the action, understand the information, complete the workflow, recover from mistakes, and tell what happened?
- Review interaction next: identify weak affordances, inconsistent state transitions, unclear progress, preventable errors, lost input, inaccessible controls, confusing focus movement, and misleading feedback.
- Review visual structure against the actual brief: hierarchy, reading order, typography, color roles, contrast, spacing, density, alignment, responsive composition, imagery, and consistency; critique a mismatch with evidence instead of prescribing a personal style.
- Review implementation for maintainable reuse, semantic markup, accessibility, correct state ownership, verified responsive behavior, rendering performance, dependency fit, and unintended changes outside the target.
- Assess intrinsic task complexity separately from avoidable cognitive load; look for too many simultaneous decisions, memory bridges, hidden navigation, jargon, competing emphasis, inconsistent patterns, multitasking, and disruptive context switches.
- Apply the ten heuristics in context: system status, real-world language, user control, consistency, prevention, recognition over recall, efficiency, minimalism, useful error recovery, and help; mark genuinely inapplicable criteria as such.
- Use representative behavior scenarios for a frequent user, first-time visitor, accessibility-dependent user, deliberate edge-case tester, and distracted mobile visitor; these are inspection lenses, not claims that user research occurred.
- For scores, disclose the rubric, applicable criteria, weighting, observed scope, and evidence limits; avoid unsupported precision and never let an aggregate score hide a critical blocker.
- For accessibility, verify semantics, names, labels, keyboard operation, focus visibility and restoration, dialogs, live feedback, contrast, text resizing, target size, reduced motion, and alternative input as applicable; follow [accessibility](accessibility.md) for the full criteria.
- For responsive and platform checks, inspect the actual shipped layouts and devices, long/localized content, safe areas, input method, overflow, and dynamic text; native evidence comes from the relevant simulator or device rather than a browser mockup.
- For performance findings, distinguish a measured bottleneck from a suspicious pattern; capture the interaction, conditions, device, and measurement, and route through [optimize](../upstream/impeccable/reference/optimize.md), [react-performance](react-performance.md), and [interaction-motion](interaction-motion.md).
- For implementation integrity, verify that visible controls work, real content and states are represented, routes exist, assets load, responsive variants are genuine, and unsupported claims or fabricated proof have not been introduced.
- Load [break-ui](../upstream/emil/skills/break-ui/overview.md) and its full [worst-case catalog](../upstream/emil/skills/break-ui/CATALOG.md) to inspect long names, identifiers, labels, large and signed numbers, dates, empty or huge collections, missing media, partial states, and adverse environments.
- Keep adversarial fixtures and prototype toggles development-only, use temporary or existing test mechanisms within scope, and never overwrite real data or silently add production routes; report whether the tested cases were actually exercised.
- Use [harden](../upstream/impeccable/reference/harden.md) for overflow, localization, validation, errors, permissions, boundaries, accessibility resilience, performance resilience, and production-state verification when implementation changes are requested.
- Use [polish](../upstream/impeccable/reference/polish.md) for a final whole-path quality pass and [craft floor](../upstream/impeccable/reference/craft-floor.md) for the full rendered quality checklist; interpret source aesthetic bans through the host brief and project identity.
- When a visual reference is authoritative, measure composition, region relationships, scale, cropping, typography, palette, and assets against it; use [component review](../upstream/impeccable/reference/component-review.md) and [finish-reviewer guidance](../upstream/impeccable/agents/impeccable-finish-reviewer.md) for evidence quality and fidelity assessment.
- An independent reviewer can reduce anchoring when the task justifies one; provide the actual brief, changed files, relevant screenshots, target sizes, and open questions, and report honestly if the review happened in the same context or without a browser.
- Do not claim that an upstream detector, live overlay, specialized agent, or approval receipt ran; this pack contains their documentation, and review must use capabilities actually available in the current environment.
- Report each material finding as location, evidence, user impact, severity, smallest useful fix, and verification; separate a reproduced defect from a likely risk and from an optional design direction.
- Prioritize lost functionality, inaccessible paths, incorrect outcomes, unrecoverable data/input loss, and confusing critical actions before minor visual inconsistency; use severity relative to users and task rather than the reviewer’s irritation.
- Include what works and the boundaries of the review, but do not bury high-impact findings under a checklist or manufacture issues to fill every category; group repeated symptoms by their systemic cause.
- When fixing is authorized, batch related corrections, rerun the checks that cover the changed behavior, compare before and after under the same conditions, and stop when the requested goal and required gates are satisfied.
- If a check cannot run, name the missing evidence and its practical limit; keep unresolved items open instead of reporting them as fixed, and avoid expanding verification without a concrete remaining risk.
- For learning from design corrections, use [learn-taste](../upstream/emil/skills/learn-taste/overview.md) to separate durable evidence-backed rules from one-off preferences, detect conflicts, and retain the reason; update only authorized project documentation, never the global UIUX skill.
- Upstream reporting tables, named personas, scores, artifact names, approval prompts, and maintenance commands are reference formats; use the user’s requested report shape and project documentation conventions, including flat one-line design-policy bullets where required.
