- Use this guide when React component variants, boolean mode props, compound components, render props, context providers, or shared state make the component API hard to understand; preserve an existing simple API when it already fits.
- This index covers all eight rules in the pinned Vercel snapshot; each linked rule retains its complete explanation and contrasting examples, and the [complete guide](../upstream/vercel/composition-patterns/complete-guide.md) is available for a comprehensive architecture audit.
- Prefer composition, deliberate state ownership, reusable internals, and explicit variants; separate these concerns without introducing providers, registries, or abstractions that the actual component does not need.
- [architecture-avoid-boolean-props](../upstream/vercel/composition-patterns/rules/architecture-avoid-boolean-props.md): replace growing combinations of behavioral modes such as thread/edit/direct-message booleans with composable pieces and named variants so consumers can see the rendered structure and impossible combinations disappear.
- [architecture-compound-components](../upstream/vercel/composition-patterns/rules/architecture-compound-components.md): expose cohesive subcomponents for a complex control and share the control's state through its local context; consumers compose the pieces they need while the provider injects state, actions, and metadata.
- [state-decouple-implementation](../upstream/vercel/composition-patterns/rules/state-decouple-implementation.md): make the provider the only layer that knows whether state comes from local hooks, an existing store, or server synchronization; UI pieces consume the stable context contract and remain reusable across state implementations.
- [state-context-interface](../upstream/vercel/composition-patterns/rules/state-context-interface.md): define a typed contract with `state`, `actions`, and `meta` so interchangeable providers can supply behavior and refs; previews or submit controls may consume that contract outside the visual frame when they remain inside the provider.
- [state-lift-state](../upstream/vercel/composition-patterns/rules/state-lift-state.md): lift shared state to the nearest deliberate provider boundary so sibling previews, dialogs, and actions can read or change it without prop-drilling, redundant synchronization effects, or imperative access to private child state.
- [patterns-explicit-variants](../upstream/vercel/composition-patterns/rules/patterns-explicit-variants.md): give materially different use cases explicit variant components that declare their provider, rendered parts, and available actions while reusing the common internals; avoid hidden mode combinations.
- [patterns-children-over-render-props](../upstream/vercel/composition-patterns/rules/patterns-children-over-render-props.md): compose static structure with `children` and ordinary components instead of proliferating `renderX` props; retain render props when the parent must provide data or state to the child.
- [react19-no-forwardref](../upstream/vercel/composition-patterns/rules/react19-no-forwardref.md): only on React 19+ with compatible types, a ref can be an ordinary prop and `use(Context)` can read context conditionally; React 18 and earlier require their existing APIs, and a composition cleanup does not authorize a framework upgrade.
- Apply the React 19 version gate to every example using `use(Context)` or the context object as a provider, including the other seven rules; keep context providers and context reads within supported client boundaries because Server Components cannot read client context; these examples also contain illustrative React Native-style controls, so adapt to the project's web primitives and accessible semantics.
- The upstream wording that `use()` replaces `useContext()` describes an available modern pattern, not a requirement to rewrite working code; [React's context documentation](https://react.dev/reference/react/useContext) still documents `useContext`, and [the use API](https://react.dev/reference/react/use) explains conditional context reads.
- Verify variants independently, provider boundaries, default and missing state, keyboard behavior, focus, refs, loading/error states, and the component's existing consumers after changing its API; test shared-state behavior rather than merely duplicating implementation details.
- For existing React Native/Expo applications or React View Transition work, use the [Vercel on-demand catalog](../upstream/vercel/CATALOG.md) and only its relevant platform rules or animation chapter.
